# Evaluation Approach

We evaluate your submission holistically. There is no point-per-checkbox system.

## What matters most

**Architecture & code quality** — Can another developer join this project tomorrow and be productive? Is the code organized logically? Are responsibilities clear?

**Product thinking** — Did you build something a real field sales rep would find useful? Are the interactions thoughtful or just technically functional?

**Decision-making** — The assignment is intentionally underspecified in places. We want to see how you make trade-offs and whether you can articulate *why* in your SUBMISSION.md.

**Robustness** — Does the app handle real-world conditions? Network drops, empty data, permission denial, rapid user interaction, device rotation.

## What matters less

- Visual design polish (functional UI > pixel-perfect)
- Completing all 5 phases (depth > breadth)
- Using bleeding-edge libraries (stable, well-understood choices are fine)

## Phases as signal

| Phases Completed | Signal |
|-----------------|--------|
| Phase 1 only | Below bar unless architecture is exceptional |
| Phase 1-2 solid | Meets bar — shows Android + maps competence |
| Phase 1-3 solid | Strong — shows ability to build real features |
| Phase 1-4 solid | Very strong — shows production-readiness thinking |
| Phase 1-5 solid | Exceptional |

A polished Phase 1-2 with great SUBMISSION.md outranks a buggy Phase 1-5.
